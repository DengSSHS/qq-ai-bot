# QQ 掉线看护（qqguard.py）

## 为什么需要它

2026-10-24 的真实事故：

```
07:25:15  [KickedOffLine] 你的账号当前登录已失效，请重新登录
07:25:24  没有 -q 指令指定快速登录，将使用二维码登录方式
19:18     有人上去查 —— 中间 12 小时，一条消息都没回
```

掉线本身不可怕，可怕的是**没人知道**。

## 根因：entrypoint 与内部重启的区别

`/app/entrypoint.sh`：

```bash
if [ -n "${ACCOUNT}" ]; then
  gosu napcat /opt/QQ/qq --no-sandbox -q $ACCOUNT   # 带 -q → 可快速登录
else
  gosu napcat /opt/QQ/qq --no-sandbox                # 不带 → 只能扫码
fi
```

| 场景 | 走哪里 | 带 `-q` | 结果 |
|---|---|---|---|
| 容器重启 | entrypoint | ✅ | 用保存的 token 自动登录 |
| 被踢后 | NapCat 内部重启 worker | ❌ | 只能扫码等人 |

所以**掉线后重启容器**是一个可用的自愈手段：token 还有效就能免扫码恢复。

## 状态机

```
在线 ──断线──> 等新事件 ──看到 KickedOffLine──> 重启容器
                                  ├─ 连上了 → 回「在线」，若掉线 >5 分钟就告知主人
                                  └─ 没连上但有二维码 → 「等人工」，发邮件，停手
```

还有一条**平行判定**（2026-10-24 深夜补上，见下节）：

```
WS 连着 ──日志里出现「登录态已失效」/ 盘里有待扫的二维码──> 「假在线」，直接发邮件
```

四条防呆：

1. **只认 checkpoint 之后的新事件**。否则每轮都看到旧的 KickedOffLine 就重启，
   会把主人正在扫的二维码刷掉。
2. **一小时最多 3 次**。和风控硬碰没有意义。
3. **进入「等人工」后不再重启**，让二维码留在那里。
4. **假在线不重启**，只告警。「登录态失效」重启只是换一张新码，
   反而会把人工正在扫的那张刷掉。

## 假在线：WS 连着不等于她还在线

2026-10-24 22:51，她突然一句话都不回。但看护的判断是「在线」——因为
OneBot 的反向 WebSocket 一直是 `ESTAB`。

真实状态是：腾讯把登录态作废了，QQ 客户端已经退出登录，只有 daemon 的
WebSocket 还挂着。这种状态的特征是：

| 信号 | 断线 | 假在线 |
|---|---|---|
| OneBot WS（8643） | 断 | **连着** |
| 容器进程 | 活 | 活 |
| 群里发消息 | 收不到 | **也收不到** |
| 看护判断 | 断线 | **在线（错）** |

所以只看连接状态的看护，对这种情况**完全盲**。补的判定是直接读 NapCat 日志：

```
登录态已失效 / 用户身份已失效 / 请扫描下面的二维码 / 需要验证码 / Login Error,ErrType
```

或者容器里 10 分钟内新生成的 `qrcode.png`（说明此刻正等人扫）。
命中任一 → 判定「连着但登录态失效」→ **发邮件**（不带重启）。
识别逻辑抽成了纯函数 `classify_log()`，由 `tests/test_qqguard_logout.py` 盯着，
NapCat 改日志文案会立刻红。

## 为什么告警走邮件

QQ 掉线时出站通道也断，`qq_send_*` 发不出去。邮箱是唯一必然还通的渠道
（而且 QQ 号自带 QQ 邮箱）。

## 直连发送：绕开机器人自己发（2026-10-24 补）

发现一个比“没告警”更阴的问题：**日志说“已告知主人”，主人手机上什么都没有**。

原因：告警靠注入通道（`qq-inject.jsonl`）把话交给机器人，让她转告。
但注入轮次**不会自动回发**（那是给“主动说话/写日记”这类内部提示用的，
纯文字发送靠插件“收到消息→自动回发”实现，注入不走这条路）。

所以现在改成**服务器直连发送**：

```
qqguard ──HTTP POST /send_private_msg──> NapCat ──> 主人的 QQ
```

一次性开启（幂等，登录过一次之后跑）：

```bash
python3 scripts/enable_napcat_http.py    # 在 /opt/qqbot/data/config 里加 httpServers :3000
# 需要重启 NapCat 容器生效——重启一般要重新扫码
```

端口绑容器的 `0.0.0.0:3000`，但**只在内 docker 内网可达**；宿主机用容器 IP 访问，
公网碰不到。token 复用反向 WS 那个，不新增密钥。

现在日志会区分三种真实结果：

| 日志 | 含义 |
|---|---|
| `已直接发到 QQ（message_id …）` | 真发出去了 |
| `已注入（不保证真的发到了 QQ）` | 直连失败，退回旧路子 |
| `通知未发出` | 两条都不行 |

顺带得到个更准的在线判定：`online_confirmed()` 直接问 NapCat 的 `get_status`，
比看 WS 是否 `ESTAB`、比翻日志找关键字都可靠。

配置 `mail.env`：

```
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_USER=<BOT_QQ>@qq.com       # 发信方，默认从 BOT_QQ 推导
SMTP_PASS=<16 位授权码>          # 不是 QQ 密码
MAIL_TO=<OWNER_QQ>@qq.com       # 收信方，默认从 OWNER_QQ 推导
```

## 踩过的坑

**授权码配错时的报错极具误导性。**

填 QQ 密码（而不是授权码）得到的是：

```
发送失败: Connection unexpectedly closed
```

完全不提认证失败，看起来像网络问题或 TLS 问题。实测同一把钥匙分别试两个邮箱，
只有配对的那个能登录——所以遇到这个报错，先怀疑「钥匙和账号不配对」。

获取授权码：QQ 邮箱网页版 → 设置 → 账号 → POP3/IMAP/SMTP 服务 → 开启 → 生成。
**只显示一次**，关掉就没了。

## 日常查看

```bash
python3 /opt/dsh/qqguard.py --status    # 连接状态 / 本小时重启次数 / 最近事件
cat /opt/dsh/memory/qq-incidents.log    # 完整事件流水
```

QQ 恢复后 `--status` 里的「本小时重启次数」会重置——它是按成功连接来清的，
不是按时间窗。
