新增一个**可选模块**：她能自己去 B 站看视频、读字幕，觉得有意思就在评论区 **@ 主人**——
主人会收到 B 站通知，点进去就是那个视频。

不装不影响任何功能。

## 为什么站在 Tulpa 上

B 站的 wbi 签名每天轮换，还要 buvid3、SSRF 防护、字幕解析、视频抽帧。
[Tulpa](https://github.com/fumingyang2004/Tulpa) 全做完了，而且更谨慎
（DNS 固定、URL 白名单、拒回环/私网、媒体缓存配额）。

自己从零写要多两周，而且大概率没有它安全。

## 读和写为什么要分开

Tulpa 是**明确只读**的（net.py 只放行 GET 路由）。发评论是 POST，它不提供。

```
读   Tulpa          搜索 / 推荐流 / 详情 / 字幕+抽帧 / 评论列表
写   bili_at.py     用同一个 cookie 发评论、@ 指定的人、删自己刚发的
```

不改 Tulpa 的安全层——它的只读保证不被破坏。

## 中间为什么还要一层代理

第一版是把她直连 Tulpa 的 MCP，然后用「开关 MCP」来做时间窗。**实测失败**：

```
dsh 的 MCP 连接是启动时建立的。关掉再开，dsh 不会重连——
工具名还在她的工具表里，但每次调用都失败。
她的原话："窗口已经开了，但我手里好像没有能把视频内容读出来的那个工具。"
```

改成：**Tulpa 的 MCP 一直开着，时间窗的判断放在代理 bili_hub.py 里**。
代理是 stdio 常驻，dsh 启动就连上，永不掉线。

## 三层闸门

| 层 | 管什么 | 默认 |
|---|---|---|
| **时间窗** | 低谷能自己刷、高峰不许、手动授权 | 23:30-08:00，每天叫醒 3 次 |
| **token 预算** | 每天浏览的 token 上限 | **关闭**（enabled=false） |
| **分享配额** | 评论区 @ 主人的频率 | 3 条/天、间隔 20 分钟、同视频 7 天一次 |

### 时间窗：累积随机而不是固定整点

低谷期**每多待一小时，「叫醒她」的概率抬一档**（+25%，封顶 90%）。
同一小时内只掷一次骰（小时桶哈希），换小时才重掷。

掷中就注入一条：「（现在是你的时间）去 B 站刷刷吧，看到有意思的记得在评论区 @ 我。」

主人在对话里说「给你玩 30 分钟」→ 她调 `bili_open(30)` 开窗口，到点自动关。

### token 预算：为什么不复用 usage.jsonl

那里记的是整轮模型调用，**无法归因**到"因为刷 B 站"。所以按**工具返回内容的体量**估算：
中文约 2 字 = 1 token。她自己能随时用 `bili_budget` 查还剩多少。

默认关闭——因为这个量级通常不需要限制（见下）。

## 实测结果

```
读     search_videos 返回真实结果（BV号/标题/UP主）
       read_video 拿到 AI 中文字幕：295 条 / 3132 字 ≈ 1566 tokens
       同时抽了 4 帧（188s / 564s / 940s / 1316s）
写     code=0，主人**确实收到了 @ 通知**
       （新号评论进人工审核，游客暂时看不到，但通知照常到）
配额   重复分享被拦（too_soon / duplicate）
时间窗 高峰时段读工具返回 window_closed；bili_open 超额被拒
```

成本：一个 25 分钟视频的完整讲稿 ≈ 1566 tokens，只占一个对话回合的 1.5k。
Tulpa 常驻内存约 68 MB（systemd cgroup 实测；ps 的 RSS 会重复算共享库）。

## 踩过的坑（详见 docs/bilibili.md）

- **`-101 账号未登录` 多半不是代码问题**：同一账号不能两处同时登录，
  主人在手机上登了它，服务器这边立刻失效
- **写接口不需要 buvid3 / bili_ticket**：网上教程说要，实测纯 cookie 就够
- **只写 `@昵称` 不传 `at_name_to_mid`，对方收不到通知**——评论会显示，但不通知。
  这是这类脚本最常见的失败点
- **Linux 包有上游 bug**：`app_mcp` 已改名 `terminal_server`，引用没改
- **`GenWebTicket` 要 POST**，GET 返回 405

## 安全边界

```
她能做     看视频、读字幕、搜东西、在评论区 @ 主人（一天最多 3 条）
她不能做   点赞、关注、发动态、剪视频、上传、翻别人的私信
硬约束     B 站登录态在 Tulpa 的加密库里，只有发评论时读一次
           Tulpa 的 GET-only 白名单未改动，写入走独立进程
```

一个运维约束要记住：**主人在别处登录这个号 → 服务器这边立刻掉线**。
要么给她单独的号，要么接受"你用了她就不能用"。
