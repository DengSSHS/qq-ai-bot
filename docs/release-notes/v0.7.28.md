# v0.7.28 · 干净机端到端验证：抓出四个真 bug

用一台按小时计费的干净 Ubuntu 24.04（2 核 1.9G，默认 `ubuntu` 账号）从零跑
`tar 上传 → bash deploy.sh`。**结果比预想糟——四个 bug，其中两个会让新装机器直接残废。**

## 1. `install.sh: line 193: PY: unbound variable`

我当天引入的：在"记录基线"那段用了 `$PY`（那是 `update.sh` 的变量），
`install.sh` 里没有，`set -u` 下一个未定义变量直接崩掉整个安装。
→ 写死 `python3`。

## 2. 登录失败会中断安装 → 服务/定时器全没装

第 8 步拿不到 onebot 配置就 `exit 2`，第 9 步（systemd）**根本没执行**：

```
Unit dsh-onebot.service could not be found.
```

→ 改成登录失败只记 `PENDING_LOGIN=1`，继续装反向 WS 配置和 systemd，
最后提示"扫码后重跑 install.sh"。实测 9/9 步走完、`dsh-onebot 运行中`。

## 3. **所有 MCP 被 dsh 禁用**（最严重）

```
disabling profile plugin row "mcp-vision": Plugin @deepseek-ai/dsh-mcp-client@0.0.1-rc.1
is incompatible with dsh 0.2.1-rc.2 ... Exact-version exemption: not active
```

记忆、看图、联网、生图、表情、管理工具**全被禁用**，只剩聊天能用。

真因：生产机上有 `profiles/web/compatibility.json`（版本豁免名单），
**是作者手工加的，安装脚本从来没创建过它**：

```json
{ "@deepseek-ai/dsh-mcp-client@0.0.1-rc.1": ["0.2.1-rc.2"] }
```

也就是说**任何人新装都是残废版**，而且不会报错——聊天本身能用，看不出来。
→ `stack/compatibility.json` 进仓库 + `install.sh` 写入；修完 6 个 MCP 全起来。

## 4. Docker Hub 拉不到镜像

```
failed to resolve reference "docker.io/mlikiowa/napcat-docker:latest": i/o timeout
```

国内机器常见，生产机因为早就拉过所以从没暴露。
→ `install.sh` 配 `/etc/docker/daemon.json` 镜像加速（腾讯云内网优先，
实测 `mirror.ccs.tencentyun.com` 返回 200）。

## 5. `deploy.sh` 在非 root 账号下跑到一半才失败

报错是"请用 root 跑（sudo bash install.sh）"，但用户明明用的是 `bash deploy.sh`，
看起来像脚本 bug。→ `deploy.sh` 开头自动 `sudo -E` 重跑。

实测：`ubuntu` 账号直接 `bash deploy.sh` → 提示自动提权 → 一路走完。

## 验证结果（干净机，未登录 QQ）

```
RESULT: 16 passed, 2 failed
[FAIL] OneBot not connected       ← NapCat 在等扫码
[FAIL] checkall.py exit 1         ← 同一个原因
```

除扫码登录外，服务、端口、MCP、配置、人设、看图端点、bridge ready 全部通过。

## 两个没解决的设计问题

**preflight 在部署目录里必报两条**：

```
[FAIL] private endpoint leaked            ← deploy.env 里的 vision 端点
[FAIL] deploy.env must not be committed   ← 仓库目录里有 deploy.env
```

`preflight` 假设"仓库目录不该有 deploy.env"，但部署又必须放一个——
检查和部署用的是同一个目录，逻辑上冲突。没改，先记着。

**没跑到 `VERDICT: READY`**：最后一步要扫码登 QQ，会踢掉生产机的鲸鲸。
所以这次验证的结论是"**除登录外全部通过**"，不是"完全通过"。
