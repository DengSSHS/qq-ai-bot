# v0.7.21 · 更新不会覆盖别人改过的东西

> 别人自己肯定会改一些东西，但是你更新不可能把这些代码给挤掉吧。
> 不能把别人自己改的东西挤掉……这个得想个解决方法

顺着这句话去查，先发现自己的 `update.sh` 有个更基础的问题：**它根本不同步脚本**——
只同步配置和插件。所以"更新会不会覆盖改动"这个问题，当时连问都问不到。

## 解法：三方比对

```
安装/上次同步 → 每个文件的 sha256 记进 memory/deploy-manifest.json（基线）
每次更新      → 看三方：磁盘现状 / 基线 / 仓库新版
```

| 情形 | 判断 | 处理 |
|---|---|---|
| 磁盘 == 基线 | 没人动过 | **直接更新** |
| 磁盘 == 新版 | 已是最新 | 不动 |
| 磁盘 ≠ 基线 且 ≠ 新版 | **别人改过** | **绝不覆盖**：保留他的，新版写 `名.new`，报告里列出 |
| 没有基线（老机器） | 说不清 | 保守处理：同上，不覆盖 |

实测三种情形：

```
proactive.py → 更新到新版（没人改过）
notify.py    → 保留使用者改动，新版放在 notify.py.new
```

报告会给他三条路：什么都不做（继续用自己的）、拿 `.new` 覆盖、`diff -u` 看完再合。
想让当前内容成为新基线就跑 `--adopt`。

## 为什么"没有基线"要保守

老机器（这版之前装的）没有基线文件。如果这时按"没人动过"处理，
第一次更新就会把人家的改动全冲掉。所以宁可这次不更新，报给他看。

`install.sh` 现在会在部署完脚本后立刻记录基线，新装的机器不会落到这个分支。

## 边界（我要说清楚）

这套机制保护的是 **`/opt/dsh/*.py` 和 `*.sh`**，也就是脚本层。

**不保护** `node_modules` 里的插件代码：那里是靠 `install_fork.sh` 整包替换的。
如果使用者直接改了插件源码，更新会覆盖——这个限制没法用基线解决，
因为 fork 快照本身就是"整包覆盖"的语义。正确的改法是用 `apply_local_patches.py`
（补丁会在更新后自动重打）。这一点写进文档了。

## 自验

```
三方比对：三种情形全部实测（更新 / 保留 / .new 落盘）
install.sh / update.sh / sync_scripts.py 语法通过
preflight 73 / 0
```
