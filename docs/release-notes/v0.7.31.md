# v0.7.31 · 自动更新实测：三个连环 bug

用「仓库停在 v0.7.27 → 让自动更新升到 v0.7.30」做真机测试，抓出三个 bug。

## 1. detached HEAD 被误报成"本地有改动"

```
$ git checkout v0.7.27      # 停在 tag 上
发现 3 个新提交：0.7.27 → 0.7.30
失败：git pull 没能快进（本地有改动？），放弃本次更新
```

工作区明明是干净的（`nothing to commit, working tree clean`），
真因是 **HEAD detached**——`git pull --ff-only` 在 detached HEAD 上永远不能快进。

→ 新增：拉取前先判断 `git rev-parse --abbrev-ref HEAD` 是不是 `HEAD`，
是就 `git checkout -B main origin/main` 切回去。

## 2. 切完分支还在用旧提交号判断

修完第 1 条又发现：

```
已切回 main（62b6fd8 / 0.7.30）
无更新（当前 0.7.30 / 62b6fd8）
```

看起来对，但**部署还是旧的**——因为 `CUR_COMMIT` / `CUR_VER` 在切分支**之前**就取好了，
`BEHIND` 算出来是 0，于是直接"无更新"退出，`update.sh` 根本没跑。

→ 切分支后重新取变量，并置 `NEED_DEPLOY=1`：即使 `BEHIND=0` 也补一次部署。

## 3. 服务单位不存在 → 更新失败 → 回滚也失败

```
== 5/6 重启服务 ==
Failed to restart dsh-onebot.service: Unit dsh-onebot.service not found.
[失败] 重启失败
update.sh 返回非零，回滚到 ...
回滚后 update.sh 仍失败，需人工介入
```

原因是这台机器的**旧版安装**在"等扫码超时"时就 `exit 2` 了（v0.7.28 修的那个 bug），
第 9 步 systemd **根本没执行**，所以 `dsh-onebot.service` 压根不存在。
而 `update.sh` 直接 `systemctl restart` → 失败 → 回滚 → 还是失败。

→ `update.sh` 重启前先检查 unit 是否存在，不存在就先把 `stack/systemd/*` 装进去、
`daemon-reload`，再启动；重启失败只 warn（配置与脚本已经更新完，不该整体判失败）。

## 附带发现：自动更新会覆盖它自己

第一次修好 `auto_update.sh` 后跑更新，更新过程把 `/opt/dsh/auto_update.sh`
从仓库（旧 tag）同步回去了，于是下一轮又跑回旧逻辑。

这是"配方自己覆盖配方"的问题。**根因**：`update.sh` 从仓库同步脚本，
而仓库当时 checkout 在旧 tag 上。修了第 2 条（切分支后必须重新部署）之后，
这种情况会变成"先切到 main 再同步"，不会再回退。

## 还没验完的

修复已提交，但**完整的"自动更新成功"闭环还没跑通**——需要在真机上再跑一次
`bash auto_update.sh`，确认能升到 0.7.31 且服务健康。这一条我在下一版补上。
