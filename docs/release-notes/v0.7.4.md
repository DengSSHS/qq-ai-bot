# v0.7.4 · 把“没验的东西”写进 README，而不是当成没发生

v0.7.1 大改了部署链路（`deploy.sh`），按道理应该在干净机器上端到端跑一遍。
今晚讨论后放弃了，理由是成本明显高于收益——但**放弃本身要被记录下来**，
否则下次看到 README 里那行 `VERDICT: READY` 又会误以为一切都被验过。

## 尝试过的三条路

| 方案 | 真实性 | 为什么没走 |
|---|---|---|
| 临时租一台 VPS | 100% | 要花钱、要人开机，为一次验证不值得；而且装完就销毁，没有长期价值 |
| 在现有服务器上跑嵌套容器 | ~80% | 执行环境禁止系统级包安装（防污染），且 NapCat 阶段覆盖不到（容器里再跑 NapCat 容器 + 扫码不现实） |
| 本机 | 0% | 无 Docker、无 WSL、虚拟化未暴露给 Hypervisor |

## 实际改动

README 新增一节「验证到什么程度（请自己判断）」，把每个环节**验到了什么**列清楚：

```
preflight.sh   静态检查（文件引用、语法、占位符、密钥、文档一致性）   71 项，都过
单元测试        纯函数与安全边界                                    121 个用例，都过
deploy.sh      配置校验的 6 个分支                                 沙箱桩测过
verify.sh      部署实况（系统、服务、模型、真发图测看图）            在已有部署上跑过
```

并明确写出**没验的那一条**：

> 从一台全新机器开始、真的跑一遍 `install.sh` 到 `VERDICT: READY`。
> 链路本身在真实环境里被反复用过，但“从零开始一次装完”只有作者自己的部署作证，
> 没有第三方干净机验证。

最后给了使用建议：上生产前自己在一台临时机上跑 `bash deploy.sh`，看到 `VERDICT: READY` 再上。

## 为什么这件事值得单独发一版

`VERDICT: READY` 这行字有两种读法：

- 它想说：“这台机器装好了，现在能用。”
- 容易被读成：“任何人都能装得起来。”

第二条才是开源项目里别人真正关心的，而它恰好没被验证过。
写清楚边界，比留一句漂亮但含糊的验收结论更有用。

## 同一版里的第二个修复：告警真的能发出去了

查证过程中发现：`qqguard` 日志写着“已恢复，已告知主人”，但 **QQ 侧一条私聊发送记录都没有**。

根因：告警靠注入通道把话交给机器人转告，而那一轮**不会自动回发**——
纯文字回复是插件“收到消息→自动回发”实现的，注入不走这条路。

现在改成服务器直连：

```
qqguard ──HTTP POST /send_private_msg──> NapCat ──> 主人的 QQ
```

- `qqguard.py` 新增 `send_direct()` / `online_confirmed()` / `_napcat_conf()`
- 新增 `scripts/enable_napcat_http.py`（一次性开 HTTP 口，幂等：重跑后配置 md5 不变）
- 日志区分真实结果：`已直接发到 QQ（message_id …）` / `已注入（不保证真的发到了 QQ）` / `通知未发出`

实测结果：`send_direct` 返回 `已发到 1709392682（message_id 1054622311）`，手机上真的收到了。

另外得到一个更准的在线判定：`online_confirmed()` 直接问 NapCat 的 `get_status`
（`online: true, good: true`），比看 WS 是否 `ESTAB`、比翻日志找关键字都可靠。
