这一版没有新功能，改的是**长期维护方式**：把本地 fork 显式化。

起因是你提的那句——补丁数量在涨，趋势不妙。我按你说的做了长期那条（fork），
做的过程中发现一个比"补丁变多"更严重的事实。

## 纠正：这不是"原版 + 5 处补丁"，它本来就是 fork

查上游漂移时对比发现：

```
lib/bridge.js   +151 行   上游用 buildPlatformPrompt，fork 用 buildPromptParts
                          并且多传了 stickerStore
lib/prompt.js   +126 行   「Local patch: the QQ channel now owns the identity/persona」
```

而 `package.json` 里的版本号仍然写着 `0.9.3`。

**所以从外面完全看不出已经分叉。** 后果很实在：

```bash
npm install    # 只认版本号，把 registry 原版覆盖上来
               # → 约 500 行改动静默消失，零报错
```

这一天里我们反复遇到的"改了但没生效"，根因之一就是这个：**改的是快照，
跑的是 npm 装的原版。**

相对 registry 0.9.3 的实际偏移：**+493 / -37 行**。

## vendor 化

```
vendor/
  fork-YYYYMMDD/          lib/ + package.json 的完整快照（我们的工作版本）
  patches/*.patch         相对上游的完整 diff（审阅 + 合并参考）
  install_fork.sh         装回 node_modules，带语法自检
  lib-before-rebuild/     上次重建前的备份，出错可回滚
```

```bash
bash vendor/install_fork.sh --check   # node_modules 是否被覆盖
bash vendor/install_fork.sh           # 用最新快照重装
```

`install.sh` 在 `npm install` 之后**自动**调用它——这一步不能省。

实测：

```
--check        → 一致时 OK
删掉 cq.js     → --check 报 DIFF，列出缺失
install_fork   → 一键恢复 + 语法自检通过
重建后起服务   → active / OneBot 已连接 / 5 处补丁在位 / 6 个 MCP 子进程
```

## 升级语义变了

```
原来以为：升级 = 让我们 5 处补丁适配新锚点
实际是：  升级 = fork 合并（我们改过、上游也改过）
```

已核实的上游漂移（0.9.3 → 0.9.6）：

| 文件 | 变化 |
|---|---|
| `prompt.js` | 96 行 → 31 行，`readPersona()` 整个搬走 |
| `bridge.js` | 「当前时间」拼装不存在了 |
| `inbound.js` | `requireMention` 还在，但代码块格式变了 |
| `index.js` | `groupActivationMinutes` 改名/挪位 |
| `cq.js` | 没变（我们那条表情兜底仍可打） |

所以短期内**不升级是合理选择**。等真需要上游某个修复时，再做一次正式合并——
现在至少有快照、有 diff、有一键回滚，而不是靠记忆猜哪里改过。

## 补丁漂移检测（v0.4.3 的延续）

`patch_doctor.py` 继续每周跑：

```
GitHub Actions   每周一 12:00   --ci   失配标红
systemd timer    每周日 04:00   --mail 失配发邮件
```

它现在报的是"上游改了什么"，配合 vendor 就知道"我们要合并哪些文件"。

## 关于 fork 的判断线（保留在文档里）

```
≤3 处   补丁脚本够用
4-5 处  必须上漂移检测
>5 处   该 fork 了
```

实际情况比预想的更靠后：**从一开始就是 fork**，只是没人说清。

## 不需要升级的部署可以跳过这一版

它只加了 vendor 目录、安装脚本和文档，运行行为与 v0.4.3 一致
（除非你重装依赖——那时候这一版能救回被覆盖的改动）。
