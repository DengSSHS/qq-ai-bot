# 表情库的逻辑链条

> 这份文档记的是**为什么这样设计**，不是 API 说明。代码在 `stack/stickerlib.py`，
> 测试在 `tests/test_stickerlib.py`。换个人接手时，参数别乱调——每个数字后面都有实测。

---

## 一、链路

```
① 有人发表情 / 你自己收藏
        │
        ▼   入库前先过筛（sticker_ingest）
   查重 ──→ 安全判断 ──→ 记入附加层（extras）
        │
        ▼
② 想发时按场合挑（sticker_pick）
        │   按话题筛 → 按热度加权 → 避开刚发过的
        ▼
③ 拿到 id，用插件的 qq_send_sticker 发出去
```

**为什么第 ③ 步交给插件**：插件负责 mface（QQ 原生表情）、限流、白名单、审计。
本工具只负责“挑得聪明”和“入库别放进不该放的”。不重复实现发送。

---

## 二、三层数据，各管各的

| 文件 | 谁维护 | 装什么 |
|---|---|---|
| `media/onebot/stickers/stickers.json` | **插件** | id / name / file / hash / hits / lastUsed / emojiId / packageId |
| `workspace/sticker_full_tags.json` | 标注流水线 | id → scene（19 类）+ 图上文字 |
| `sticker-pack/extras.json` | **本工具** | id → pHash / 宽高比 / safe / lastPick / 入库时间 |

**关键：不要直接改插件的 `stickers.json`。**

插件在内存里持有 entries，会话中会 `scheduleSave()` 把旧数据写回。实测过：
停服状态下删掉一条死链，重启后它又冒出来了——因为插件把它写回了。
任何直接改这个文件的操作，**必须先 `systemctl stop dsh-onebot`**。

`extras.json` 是本工具自己的，插件不碰它，随便改。

## 三、挑图：为什么要加权

插件自带的 `qq_random_sticker` 是纯 `Math.random()`。问题不是“随机”，是**它不看 `hits`**——
而插件其实一直在记 `hits` 和 `lastUsed`，只是挑的时候不用。

```
权重 = (hits + 1) ^ ALPHA
       刚发过（30 分钟内）→ 权重 × RECENT_PENALTY
```

| 参数 | 默认 | 为什么是这个值 |
|---|---|---|
| `ALPHA` | **0.6** | 0 = 纯随机（还是老毛病）；1 = 线性（热门垄断）。0.6 是“有惯用但不垄断”的折中 |
| `RECENT_PENALTY` | **0.25** | 压低刚发过的，避免连着两条同一张。压到 0 会变成“绝不重复”，反而不像人 |
| `RECENT_WINDOW_S` | 1800 | 30 分钟内算“刚发过” |

测试里专门守了两件事：**热门必须明显多于冷门**，但**冷门不能被饿死**——否则又会退化成
“翻来覆去就那几张”。

## 四、去重：两层，两层都拦（第二层靠的是 16×16）

### 第一层 sha256 精确重复 → **拦**

字节完全一样。这是唯一完全可靠的判据，命中就直接拒绝。

### 第二层 pHash 近似 → **拦，但可以用 force=true 强收**

抓“同一张图的不同清晰度版本”（sha256 抓不到，它们字节不同）。

**关键在哈希分辨率。8×8 在这个库上根本不能用。**

8×8 的实测（抽 300 张 = 44850 对，条件：距离 ≤ 2 且宽高比差 ≤ 2%）：

```
命中 55 对（0.123%），抽出来看全是不同的图：
  初音-188        vs 袋鼠-ResizedImage     ← 跨系列
  鲸鱼娘-118      vs 鲸鱼娘-070            ← 同系列不同图
  鲸鱼娘-186 同时命中 6 张不同的图         ← 它的 phash 退化了，跟谁都“像”
```

**原因**：表情包多是纯色底、大头、构图简单，8×8 的 DCT 低频特征退化成同一个值。

换成 **16×16（256 bit）** 后同一批样本：

| 分辨率 | 误拦率（同批 300 张） | 同图变体召回 |
|---|---|---|
| 8×8（距离≤2） | 0.123%（55 对） | 100% |
| **16×16（距离≤2）** | **0.004%（2 对）** | **100%** |

召回率测法：40 张图各造 5 种变体（jpeg q50/q80/q95、缩 50%、缩 75%），
16×16 下全部距离 ≤ 2（最大 2）。**精度白拿一个数量级，不漏判。**

所以现在的策略是：

- `PHASH_SIZE = 16`，exact 命中（距离 ≤ 2 且比例一致）→ **直接拒收**
- 拒收信息里会显示库里那张的 id 和名字，确实不是同一张就传 `force=true`
- 库已经 4244 张，**收进重复图的代价比误挡一张新图高**

改动 `PHASH_SIZE` 后必须重算全库——旧值位数不同，跟新值比会被
`hamming` 的长度校验当成“完全不同”，判重静默失效。`--backfill` 已经按
期望长度校验，会自动重算旧格式（4245 张约 3 分钟）：

```bash
PYTHONPATH=/opt/dsh/lib python3 /opt/dsh/stickerlib.py --backfill
```

检查 pHash 是否可用：

```bash
PYTHONPATH=/opt/dsh/lib python3 -c "import PIL; print(PIL.__version__)"
```

## 五、入库安全判断：拿不到判断就不入库

群友发的图里可能混进带个人信息的（聊天截图、工牌、快递单）。机器人下次在别的场景
甩出去就是麻烦。所以入库前让多模态模型看一眼：

```
这张图适合当作 QQ 群聊里的表情包转发吗？
如果含有个人隐私（身份证、手机号、住址、工牌学号、聊天记录截图、他人私密影像）
或可能引起麻烦的内容，回答 NO 并简述理由；
如果只是普通梗图/表情/二次元图，回答 YES。
```

**为什么不用关键词粗判**：图里的敏感信息往往是**图像内容**，OCR 文字不一定命中，
模型看一眼就能判断。关键词只留作第一道粗筛（文件名/OCR 里有"身份证"之类直接拒，
省一次模型调用）。

**拿不到判断时（模型失败、没配 key）就不入库**，而不是放行。赌输一次是拿别人的隐私去发群。

**`scene` 必填**（哪怕填「杂图」）。原因见下一节。

## 五之二、收图筛选（sticker_triage）

群友发来的图会先落到 `media/onebot/media_*.jpg`。**插件给这些附件 6 小时 TTL**，
过期自动删——所以磁盘不会无限膨胀，但判断必须在这窗口内做。

`sticker_triage` 做的事：

```
扫 media/ 下 6 小时内的新图
   ├─ 模型判断：值得当表情素材吗？→ YES|场景|理由
   ├─ YES → 复制到 sticker-pack/pending/，等调 qq_save_sticker 收进去
   └─ NO  → 记 triage.jsonl（含理由），然后把原图删掉（不等 TTL）
```

**默认是 dry-run，只判断不动文件**；`apply=true` 才真的复制/删。

判断 prompt 的取向是**宁缺毋滥**——判 NO 的典型：聊天/通知/网页截图、纯文字、
模糊过曝、广告水印、别人的自拍、看不出想表达什么、竖长截屏。

实测对照（同一批里）：
```
b站-doge        → YES [卖萌可爱] 经典柴犬表情包，构图完整、神态明确且极具转发价值
鲸鲸形象        → YES [卖萌可爱] Q版鲸鱼女仆形象完整清晰
PIL 画的抽象图   → NO  纯色圆圈加微小文字缺乏构图与情绪表达
横线填充的假截图  → NO  无任何文字、表情或角色
```

**为什么要删而不是等 TTL**：一是立刻释放空间，二是留下明确的“这张为什么不收”记录，
以后想回头找“上次那张为什么没收录”有据可查（`sticker-pack/triage.jsonl`）。

**一个设计细节**：dry-run 也会写记录（避免重复花钱判断），所以 apply 时
会先“补执行”之前判断过但没动文件的那批，不重复调模型。

## 五之三、每天凌晨 3 点自动结算

`sticker-settle.timer` 每天 03:00 跑一次 `stickerlib.py --settle`，做三件事：

```
扫 media/ 下未过期的附件
   ├─ 算 sha256 → 查 triage.jsonl 缓存
   │    命中 → 直接复用结论（同一张图被反复发，不重复调模型）
   │    未命中 → 调模型判断（值得吗 / 场景 / 理由）
   ├─ 值得 → 复制到 sticker-pack/pending/
   └─ 不值得 → 删原图，记录理由
最后写一份日报到 memory/sticker-daily.log
```

**为什么要把 TTL 从 6 小时改成 30 小时**：这是这套结算的前提。

插件默认给附件 6 小时 TTL，下午两点收到的图晚上八点就没了。
凌晨 3 点结算时，前一天白天的图早就被清掉——**结算等于对着空气做**。
所以 `cordis.patch.yml` 里加了 `tempTtlHours: 30`（多留 6 小时余量）。

**为什么按 sha256 缓存而不是文件名**：同一张图被不同人反复发时，文件名每次都是
新的（`media_<时间戳>_<随机>`）。按文件名索引等于每次都要重新调模型判断一遍；
按内容哈希，判过就直接复用结论。这是省调用量的关键。

查看结算结果：

```bash
tail -30 /opt/dsh/memory/sticker-daily.log     # 每天的结算报告
cat /opt/dsh/sticker-pack/triage.jsonl | tail  # 每张图的判断记录（含理由）
systemctl list-timers sticker-settle.timer     # 下次什么时候跑
```

## 六、踩过的坑（别重犯）

**1. 空场景 = 死库存**

线上曾有 51 条群友发的动图，`scene` 是空、名字是 `[动画表情]`。
`sticker_pick` 带 `scene` 筛选时会把空场景整段跳过 → 它们入库了但**永远发不出去**，
白占空间。正好是“群友发图 → 存下来 → 下次能发”这条链路的最后一环断掉。

修法：`scene` 改必填；`pick` 不传 scene 时全库挑；存量 51 条补标「杂图」。

**2. 名字不能是 `[动画表情]`**

NapCat 给动图的默认名。这种名字 `query` 也匹配不到。统一改成「场景-短id」。

**3. 标签文件会缺失条目**

标注文件（4194）和索引（4245）条数曾经不一致。`sticker_pick` 要能容忍
“索引有、标注无”——现在这类会显示「未标注（不传 scene 才挑得到）」。

**4. 大库要回填 pHash**

pHash 只能在能解码图片时算。存量图是早先入库的，没有这个字段——
不回填的话“新图查近似重复”根本没东西可比：

```bash
PYTHONPATH=/opt/dsh/lib python3 /opt/dsh/stickerlib.py --backfill
```

断点续跑，分批落盘。现在（16×16）4245 张约 3 分钟；早期的 8×8 只要 77 秒——
多花的两分钟换来误拦率降一个数量级，很便宜。

**5. 只列标签名，模型会把 65% 倒进最泛的那一类**

重分类 754 张「杂图」时，第一版 prompt 只列了标签名。结果 29 张样本里 19 张
判成「卖萌可爱」——那一类本来就有 683 张。等于把杂图换个桶倒进去，结构没改善。

修法：每个标签后面跟一句**适用条件**，再加三条硬规则：

- 「卖萌可爱」只给**真的在卖萌**的（比心、蹭、眨眼、主动示好）。
  图里角色长得可爱但表达的是别的情绪，选那个情绪，不要选它。
- 有明确情绪就一定选那个情绪标签，不许往「杂图」「卖萌可爱」里塞。
- 只有纯风景、纯文字、设定图、logo 这类完全看不出情绪的才填「杂图」。

同一批样本：「卖萌可爱」从 65% 降到 24%，散布到 11 个标签。

**6. 小样本验证会骗人：串行 29/29，并发 754 张格式全崩**

同一个 prompt，29 张串行跑完美命中。并发跑到 754 张时模型开始出花样：

```
标签|一句话理由 忙工作|电脑加载中      ← 把 prompt 里的格式模板原样抄了
结合这九宫格的整体氛围，最贴的标签是：**卖萌可爱**   ← 加前缀 + markdown
我无法对这张图进行分类。                    ← 直接拒绝
```

所以解析必须三层兜底，一层都不能省：

1. 找 `{...}` 解析 JSON
2. 清洗标签字段（去 `**`、去「标签：」前缀、容忍括号补充）
3. 全文搜标签——**长的先匹配**，否则「杂图」会抢先命中任何一句话

`max_tokens` 也要给够。设 120 时，带理由的输出经常被截断在半句话上。

**7. 标注文件的 id 是 dict 的键，不是值里的字段**

`sticker_full_tags.json` 的结构是 `{"<id>": {"name":..., "file":..., "scene":...}}`。
写 `v.get('id')` 拿到的是 `None`，所有记录互相覆盖——当时 267 条结果只剩 1 条
“有效”，差点以为整轮分类废了。正确写法是遍历 `.items()` 拿键。

**重分类的成果**（754 张杂图 → 741 张成功，98.3%）：

| 场景 | 前 | 后 | | 场景 | 前 | 后 |
|---|---|---|---|---|---|---|
| 杂图 | 754 | 97 | | 疑问困惑 | 169 | 229 |
| 卖萌可爱 | 683 | 861 | | 忙工作 | 142 | 152 |
| 无语尴尬 | 270 | 377 | | 期待等待 | 63 | 86 |
| 嘲讽怼人 | 333 | 401 | | 打招呼 | 74 | 81 |
| 开心笑 | 326 | 385 | | 拒绝不要 | 34 | 39 |

杂图占比 17.8% → 2.3%。落回杂图的 84 张理由都站得住：三视图、角色设定图、
品牌 logo、纪念钞设计稿——本来就不是表情包。

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `STICKER_ALPHA` | 0.6 | 热度权重指数，越大越偏向热门 |

## 八、还没解决的

**丰富度**。库存 4244 张，但真实用过的长期停在 50 张上下（1.2%）。
加权挑图是第一刀，但“她习惯用某几张”这件事，最终可能要靠硬约束
（比如“同一张一周内别发第二次”）而不是权重。

补一句：杂图重分类救回 657 张进具体场景（见坑 5-7），可用库存涨了 17.8%，
但**这个数字不等于使用率会跟着涨**。分类修好只是让“想用某类时挑得到”，
她实际会不会去挑，还得看上面这个 1.2%。

**近似重复已改成拦**（见第四节）。754 张重分类后同类图更集中了，
16×16 下的命中主要是“同图不同编码”（实测找出一对：`菲比-哎呀` 和
`菲比-1哎呀`，距离 0、sha256 不同——典型的重复入库）。
但**误拦率仍是抽样估计**：目前只在 300 张的样本上测过（2 对命中，0.004%），
全库两两比是 900 万对，工程太大没做。如果以后出现“明明是新图却被说重复”，
优先看那个 `force=true` 出口，而不是把阈值调宽。

`sticker_stats` 能直接看出这个比例有没有变宽。
