# 表情库的逻辑链条

> 这份文档记的是**为什么这样设计**，不是 API 说明。代码在 `stack/stickerlib.py`，
> 测试在 `tests/test_stickerlib.py`。换个人接手时，参数别乱调——每个数字后面都有实测。

---

## 一、链路

```
① 有人发表情 / 你自己收藏
        │
        ▼   入库前先过筛（sticker_ingest）
   查重 ──→ 安全判断 ──→ 记入附加层（extras）
        │
        ▼
② 想发时按场合挑（sticker_pick）
        │   按话题筛 → 按热度加权 → 避开刚发过的
        ▼
③ 拿到 id，用插件的 qq_send_sticker 发出去
```

**为什么第 ③ 步交给插件**：插件负责 mface（QQ 原生表情）、限流、白名单、审计。
本工具只负责“挑得聪明”和“入库别放进不该放的”。不重复实现发送。

---

## 二、三层数据，各管各的

| 文件 | 谁维护 | 装什么 |
|---|---|---|
| `media/onebot/stickers/stickers.json` | **插件** | id / name / file / hash / hits / lastUsed / emojiId / packageId |
| `workspace/sticker_full_tags.json` | 标注流水线 | id → scene（19 类）+ 图上文字 |
| `sticker-pack/extras.json` | **本工具** | id → pHash / 宽高比 / safe / lastPick / 入库时间 |

**关键：不要直接改插件的 `stickers.json`。**

插件在内存里持有 entries，会话中会 `scheduleSave()` 把旧数据写回。实测过：
停服状态下删掉一条死链，重启后它又冒出来了——因为插件把它写回了。
任何直接改这个文件的操作，**必须先 `systemctl stop dsh-onebot`**。

`extras.json` 是本工具自己的，插件不碰它，随便改。

## 三、挑图：为什么要加权

插件自带的 `qq_random_sticker` 是纯 `Math.random()`。问题不是“随机”，是**它不看 `hits`**——
而插件其实一直在记 `hits` 和 `lastUsed`，只是挑的时候不用。

```
权重 = (hits + 1) ^ ALPHA
       刚发过（30 分钟内）→ 权重 × RECENT_PENALTY
```

| 参数 | 默认 | 为什么是这个值 |
|---|---|---|
| `ALPHA` | **0.6** | 0 = 纯随机（还是老毛病）；1 = 线性（热门垄断）。0.6 是“有惯用但不垄断”的折中 |
| `RECENT_PENALTY` | **0.25** | 压低刚发过的，避免连着两条同一张。压到 0 会变成“绝不重复”，反而不像人 |
| `RECENT_WINDOW_S` | 1800 | 30 分钟内算“刚发过” |

测试里专门守了两件事：**热门必须明显多于冷门**，但**冷门不能被饿死**——否则又会退化成
“翻来覆去就那几张”。

## 四、去重：两层，两层都拦（第二层靠的是 16×16）

### 第一层 sha256 精确重复 → **拦**

字节完全一样。这是唯一完全可靠的判据，命中就直接拒绝。

### 第二层 pHash 近似 → **拦，但可以用 force=true 强收**

抓“同一张图的不同清晰度版本”（sha256 抓不到，它们字节不同）。

**关键在哈希分辨率。8×8 在这个库上根本不能用。**

8×8 的实测（抽 300 张 = 44850 对，条件：距离 ≤ 2 且宽高比差 ≤ 2%）：

```
命中 55 对（0.123%），抽出来看全是不同的图：
  初音-188        vs 袋鼠-ResizedImage     ← 跨系列
  鲸鱼娘-118      vs 鲸鱼娘-070            ← 同系列不同图
  鲸鱼娘-186 同时命中 6 张不同的图         ← 它的 phash 退化了，跟谁都“像”
```

**原因**：表情包多是纯色底、大头、构图简单，8×8 的 DCT 低频特征退化成同一个值。

换成 **16×16（256 bit）** 后同一批样本：

| 分辨率 | 误拦率（同批 300 张） | 同图变体召回 |
|---|---|---|
| 8×8（距离≤2） | 0.123%（55 对） | 100% |
| **16×16（距离≤2）** | **0.004%（2 对）** | **100%** |

召回率测法：40 张图各造 5 种变体（jpeg q50/q80/q95、缩 50%、缩 75%），
16×16 下全部距离 ≤ 2（最大 2）。**精度白拿一个数量级，不漏判。**

所以现在的策略是：

- `PHASH_SIZE = 16`，exact 命中（距离 ≤ 2 且比例一致）→ **直接拒收**
- 拒收信息里会显示库里那张的 id 和名字，确实不是同一张就传 `force=true`
- 库已经 4244 张，**收进重复图的代价比误挡一张新图高**

改动 `PHASH_SIZE` 后必须重算全库——旧值位数不同，跟新值比会被
`hamming` 的长度校验当成“完全不同”，判重静默失效。`--backfill` 已经按
期望长度校验，会自动重算旧格式（4245 张约 3 分钟）：

```bash
PYTHONPATH=/opt/dsh/lib python3 /opt/dsh/stickerlib.py --backfill
```

检查 pHash 是否可用：

```bash
PYTHONPATH=/opt/dsh/lib python3 -c "import PIL; print(PIL.__version__)"
```

## 五、入库安全判断：拿不到判断就不入库

群友发的图里可能混进带个人信息的（聊天截图、工牌、快递单）。机器人下次在别的场景
甩出去就是麻烦。所以入库前让多模态模型看一眼：

```
这张图适合当作 QQ 群聊里的表情包转发吗？
如果含有个人隐私（身份证、手机号、住址、工牌学号、聊天记录截图、他人私密影像）
或可能引起麻烦的内容，回答 NO 并简述理由；
如果只是普通梗图/表情/二次元图，回答 YES。
```

**为什么不用关键词粗判**：图里的敏感信息往往是**图像内容**，OCR 文字不一定命中，
模型看一眼就能判断。关键词只留作第一道粗筛（文件名/OCR 里有"身份证"之类直接拒，
省一次模型调用）。

**拿不到判断时（模型失败、没配 key）就不入库**，而不是放行。赌输一次是拿别人的隐私去发群。

**`scene` 必填**（哪怕填「杂图」）。原因见下一节。

## 五之二、收图筛选（sticker_triage）

群友发来的图会先落到 `media/onebot/media_*.jpg`。**插件给这些附件 6 小时 TTL**，
过期自动删——所以磁盘不会无限膨胀，但判断必须在这窗口内做。

`sticker_triage` 做的事：

```
扫 media/ 下 6 小时内的新图
   ├─ 模型判断：值得当表情素材吗？→ YES|场景|理由
   ├─ YES → 复制到 sticker-pack/pending/，等调 qq_save_sticker 收进去
   └─ NO  → 记 triage.jsonl（含理由），然后把原图删掉（不等 TTL）
```

**默认是 dry-run，只判断不动文件**；`apply=true` 才真的复制/删。

判断 prompt 的取向是**宁缺毋滥**——判 NO 的典型：聊天/通知/网页截图、纯文字、
模糊过曝、广告水印、别人的自拍、看不出想表达什么、竖长截屏。

实测对照（同一批里）：
```
b站-doge        → YES [卖萌可爱] 经典柴犬表情包，构图完整、神态明确且极具转发价值
鲸鲸形象        → YES [卖萌可爱] Q版鲸鱼女仆形象完整清晰
PIL 画的抽象图   → NO  纯色圆圈加微小文字缺乏构图与情绪表达
横线填充的假截图  → NO  无任何文字、表情或角色
```

**为什么要删而不是等 TTL**：一是立刻释放空间，二是留下明确的“这张为什么不收”记录，
以后想回头找“上次那张为什么没收录”有据可查（`sticker-pack/triage.jsonl`）。

**一个设计细节**：dry-run 也会写记录（避免重复花钱判断），所以 apply 时
会先“补执行”之前判断过但没动文件的那批，不重复调模型。

## 五之三、每天凌晨 3 点自动结算

`sticker-settle.timer` 每天 03:00 跑一次 `stickerlib.py --settle`，做三件事：

```
扫 media/ 下未过期的附件
   ├─ 算 sha256 → 查 triage.jsonl 缓存
   │    命中 → 直接复用结论（同一张图被反复发，不重复调模型）
   │    未命中 → 调模型判断（值得吗 / 场景 / 理由）
   ├─ 值得 → 复制到 sticker-pack/pending/
   └─ 不值得 → 删原图，记录理由
最后写一份日报到 memory/sticker-daily.log
```

**为什么要把 TTL 从 6 小时改成 30 小时**：这是这套结算的前提。

插件默认给附件 6 小时 TTL，下午两点收到的图晚上八点就没了。
凌晨 3 点结算时，前一天白天的图早就被清掉——**结算等于对着空气做**。
所以 `cordis.patch.yml` 里加了 `tempTtlHours: 30`（多留 6 小时余量）。

**为什么按 sha256 缓存而不是文件名**：同一张图被不同人反复发时，文件名每次都是
新的（`media_<时间戳>_<随机>`）。按文件名索引等于每次都要重新调模型判断一遍；
按内容哈希，判过就直接复用结论。这是省调用量的关键。

查看结算结果：

```bash
tail -30 /opt/dsh/memory/sticker-daily.log     # 每天的结算报告
cat /opt/dsh/sticker-pack/triage.jsonl | tail  # 每张图的判断记录（含理由）
systemctl list-timers sticker-settle.timer     # 下次什么时候跑
```

## 六、踩过的坑（别重犯）

**1. 空场景 = 死库存**

线上曾有 51 条群友发的动图，`scene` 是空、名字是 `[动画表情]`。
`sticker_pick` 带 `scene` 筛选时会把空场景整段跳过 → 它们入库了但**永远发不出去**，
白占空间。正好是“群友发图 → 存下来 → 下次能发”这条链路的最后一环断掉。

修法：`scene` 改必填；`pick` 不传 scene 时全库挑；存量 51 条补标「杂图」。

**2. 名字不能是 `[动画表情]`**

NapCat 给动图的默认名。这种名字 `query` 也匹配不到。统一改成「场景-短id」。

**3. 标签文件会缺失条目**

标注文件（4194）和索引（4245）条数曾经不一致。`sticker_pick` 要能容忍
“索引有、标注无”——现在这类会显示「未标注（不传 scene 才挑得到）」。

**4. 大库要回填 pHash**

pHash 只能在能解码图片时算。存量图是早先入库的，没有这个字段——
不回填的话“新图查近似重复”根本没东西可比：

```bash
PYTHONPATH=/opt/dsh/lib python3 /opt/dsh/stickerlib.py --backfill
```

断点续跑，分批落盘。现在（16×16）4245 张约 3 分钟；早期的 8×8 只要 77 秒——
多花的两分钟换来误拦率降一个数量级，很便宜。

**5. 只列标签名，模型会把 65% 倒进最泛的那一类**

重分类 754 张「杂图」时，第一版 prompt 只列了标签名。结果 29 张样本里 19 张
判成「卖萌可爱」——那一类本来就有 683 张。等于把杂图换个桶倒进去，结构没改善。

修法：每个标签后面跟一句**适用条件**，再加三条硬规则：

- 「卖萌可爱」只给**真的在卖萌**的（比心、蹭、眨眼、主动示好）。
  图里角色长得可爱但表达的是别的情绪，选那个情绪，不要选它。
- 有明确情绪就一定选那个情绪标签，不许往「杂图」「卖萌可爱」里塞。
- 只有纯风景、纯文字、设定图、logo 这类完全看不出情绪的才填「杂图」。

同一批样本：「卖萌可爱」从 65% 降到 24%，散布到 11 个标签。

**6. 小样本验证会骗人：串行 29/29，并发 754 张格式全崩**

同一个 prompt，29 张串行跑完美命中。并发跑到 754 张时模型开始出花样：

```
标签|一句话理由 忙工作|电脑加载中      ← 把 prompt 里的格式模板原样抄了
结合这九宫格的整体氛围，最贴的标签是：**卖萌可爱**   ← 加前缀 + markdown
我无法对这张图进行分类。                    ← 直接拒绝
```

所以解析必须三层兜底，一层都不能省：

1. 找 `{...}` 解析 JSON
2. 清洗标签字段（去 `**`、去「标签：」前缀、容忍括号补充）
3. 全文搜标签——**长的先匹配**，否则「杂图」会抢先命中任何一句话

`max_tokens` 也要给够。设 120 时，带理由的输出经常被截断在半句话上。

**7. 标注文件的 id 是 dict 的键，不是值里的字段**

`sticker_full_tags.json` 的结构是 `{"<id>": {"name":..., "file":..., "scene":...}}`。
写 `v.get('id')` 拿到的是 `None`，所有记录互相覆盖——当时 267 条结果只剩 1 条
“有效”，差点以为整轮分类废了。正确写法是遍历 `.items()` 拿键。

**重分类的成果**（754 张杂图 → 741 张成功，98.3%）：

| 场景 | 前 | 后 | | 场景 | 前 | 后 |
|---|---|---|---|---|---|---|
| 杂图 | 754 | 97 | | 疑问困惑 | 169 | 229 |
| 卖萌可爱 | 683 | 861 | | 忙工作 | 142 | 152 |
| 无语尴尬 | 270 | 377 | | 期待等待 | 63 | 86 |
| 嘲讽怼人 | 333 | 401 | | 打招呼 | 74 | 81 |
| 开心笑 | 326 | 385 | | 拒绝不要 | 34 | 39 |

杂图占比 17.8% → 2.3%。落回杂图的 84 张理由都站得住：三视图、角色设定图、
品牌 logo、纪念钞设计稿——本来就不是表情包。

## 七、可调参数

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `STICKER_ALPHA` | 0.6 | 热度权重指数，越大越偏向热门 |
| `STICKER_RECENT_PENALTY` | 0.25 | 刚发过的降权系数 |

改之前先看一遍第三节那张表——这两个值是拿实测误判率换来的。

## 八、还没解决的

**丰富度**。库存 4244 张，但真实用过的长期停在 50 张上下（1.2%）。
加权挑图是第一刀，但“她习惯用某几张”这件事，最终可能要靠硬约束
（比如“同一张一周内别发第二次”）而不是权重。

补一句：杂图重分类救回 657 张进具体场景（见坑 5-7），可用库存涨了 17.8%，
但**这个数字不等于使用率会跟着涨**。分类修好只是让“想用某类时挑得到”，
她实际会不会去挑，还得看上面这个 1.2%。

**近似重复已改成拦**（见第四节）。754 张重分类后同类图更集中了，
16×16 下的命中主要是“同图不同编码”（实测找出一对：`菲比-哎呀` 和
`菲比-1哎呀`，距离 0、sha256 不同——典型的重复入库）。
但**误拦率仍是抽样估计**：目前只在 300 张的样本上测过（2 对命中，0.004%），
全库两两比是 900 万对，工程太大没做。如果以后出现“明明是新图却被说重复”，
优先看那个 `force=true` 出口，而不是把阈值调宽。

`sticker_stats` 能直接看出这个比例有没有变宽。

# 附：跨群长期记忆（memory_distill.py）

跟表情库无关，但同一套思路：**存下来的东西必须有注入通道，否则等于没写。**

## 现状调查（2026-10-24）

```
notes.md 三个预留区块      全是「（还没记）」
diary/                    只有装机时那两条
五个记忆工具真实调用次数    0
workspace/AGENTS.md       2787 字节，21956 行会话里只出现 8 次
```

原因是 `agent-instructions` 插件在这个 profile 里 `disabled: true`，
`AGENTS.md` 从来不会被自动注入，只能靠她主动 `read`。记忆写进去，没人念。

## 现在的结构

```
memory/knowledge.json    机器维护的结构化知识（带 count/证据/scope）
memory/knowledge.md      完整版，给人看
workspace/AGENTS.md      托管区块（auto-memory:begin/end）← 每轮注入这份
memory_distill.py        蒸馏器，每天 03:10 跑
```

`notes.md` **不动**——`tool_notes_write` 是整文覆盖，蒸馏写进去会被她一次抹掉。

## 关键设计

**1. 单一知识池，跨群共用。** 用户的要求：学习是总体的，不是切在每个群里。
但每条带 `scope`（`all` / `g:群号` / `u:QQ`），注入时标来源，并规定
「标了群的只在该群用」。同一条在两个以上场合出现 → 自动升级为 `all`。

**2. 每条都要证据。** `count` / `first` / `last` / 来源会话。只观察到一次的
标「（单次）」，提醒别当定论。没有证据的“规律”是最容易污染长期记忆的东西。

**3. 过滤会过期的东西。** 实测第一版抽出了「接口走腾讯 tokenhub」「表情库共
4194 张」——那是运行状态不是知识，两周后就错。现在按关键词过滤（模型名/接口/
token/服务器/工作区/数量），并且丢弃“某工具只能/拿不到”这类能力断言——
实测出现过把 `qq_group_history` 说成“拿不到正文”，而 prompt 里明写着会返回。

12 个群/私聊会话 → 抽 43 条 → 过滤 8 条 → 保留 35 条。

## 注入怎么接上的

`agent-instructions` 插件禁用状态在 patch 层改不动（试过，`--dump-config`
仍显示 `disabled: true`）。所以改在 `prompt.js`（本来就已是本地 fork）：
`readAgentsMemory()` 读 `workspace/AGENTS.md`，追加到 `platform` 段。
persona 就是这么注入的，会话里能验证到（87 次命中）。

实测：注入探针消息后，新的 system 消息里出现
「## 长期记忆（workspace/AGENTS.md）」及 AGENTS.md 内容 ✅

## 注意

- 改 `prompt.js` 会被插件升级覆盖，升级后要重新打补丁（备份在
  `prompt.js.bak-memonject`）
- `AGENTS.md` 每轮进提示，所以托管区块上限 2200 字，别让它无限长
- 蒸馏每天一次全量重扫，11 个会话 11 次模型调用

# 附二：调用记账（usage_log.py）

「后台挂个计费，方便后续调用」——目标是**把每次模型调用的 token 变成可查的数据**，
而不是又一份人看不动的日志。

## 为什么要在三处接

```
llm_shim.py          主对话（走 127.0.0.1:8890 网关）
seer.py              看图判断（直连上游，绕过网关）
memory_distill.py    记忆蒸馏（直连上游）
```

只接网关会漏掉看图和蒸馏 —— 而看图恰恰是调用最密集的（表情分类一跑几百次）。
所以三处都调 `usage_log.record()`。

## 数据形状

`memory/usage.jsonl`，一行一次调用：

```json
{"ts":1792784780,"d":"2026-10-24","svc":"agent","model":"deepseek-v4.1-flash-1017",
 "in":29130,"out":10,"cached":0,"cost":null}
```

`cost` 为 `null` 表示价格没配 —— **宁可不显示，也不编一个假金额**。
价格填在 `memory/usage_prices.json`（¥/百万 token，分 in / out / cached）。

查询：`python3 usage_log.py --days 7`

## 接上第一天就发现的问题

```
distill   输入 1,428   输出 233   缓存命中 1,024   （72%）
agent     输入 29,130  输出  10   缓存命中     0   （0%）
```

同一家中转、同一个模型，蒸馏能命中缓存、主对话完全命中不了。原因基本可以确定：
**每轮提示的前缀都在变**（`当前时间` 就在 system 消息第一行），前缀一变，
后面全部失效。一轮 2.9 万输入 token 因此全按全价付。

要压成本，方向是让"每轮都变的内容"往后排，把稳定部分（人设、长期记忆、工具定义）
锁在开头。这件事没改，只记在这里。

## 定时

```
03:00 sticker-settle   收图结算
03:10 memory-distill   记忆蒸馏
23:55 usage-report     用量汇总追加到 memory/usage-daily.md
```

## 排障视角（ops_report.py）——这才是「修 bug」用的

`usage_log.py` 回答「花了多少」，`ops_report.py` 回答「哪里不对」：

```
近 24 小时：请求 3 次｜失败 0 次（0.0%）｜无 usage 的 0 次
延迟：p50 902ms｜p95 902ms｜最慢 902ms
token：输入 59,796｜输出 252｜缓存命中 1.7%

工具调用：26 次｜结果里标失败 2 次（7.7%）
  失败最多的工具：
    qq_send_image       1 次  例：OneBot action failed (retcode 1200): EventChecker
    qq_random_sticker   1 次  例：写操作频率超限…
```

所以每条记账行现在还带：`status`（HTTP 状态或 `upstream_fail`）、`dur_ms`、
`path`、`in_bytes` / `out_bytes`、`err`。**失败路径也记**——原来只在拿到 usage
时才记，等于「失败和超时的调用在账本里完全看不见」，而 bug 恰恰在那些地方。

`in_bytes` 对查「为什么每轮 2.9 万 token」很有用：一次请求体 118KB。

### ⚠️ 工具失败率的时间粒度很粗

上半部分（请求/延迟/失败）读 `usage.jsonl`，每条自带时间戳，时间准确。
下半部分（工具调用）读会话文件，只能按**文件修改时间**筛会话——一个跨天的长
会话会把几天前的旧失败算进「近 24 小时」。

实测踩过一次：报告显示「`actionRatePerMinute=2` 超限」，看着像线上配错了，
回查才发现那是昨天的记录，配置早改成 20 了。**误报比不报更坏**，所以这个数字
只能当「近期有没有异常」的信号，要定时间必须回会话里翻。

## 一次真实的成本修复：把时间从前缀挪到后缀

### 症状

```
每轮 in≈29,000 token，cached=0，命中率 0%
```

同一个中转、同一个模型，记忆蒸馏却能命中 72%（1428 里命中 1024），说明
上游**支持前缀缓存**，是我们的提示前缀每轮都在变。

### 定位过程（两次走错）

1. 先怀疑 `dsh-time-context` 插件 —— 把它 `disabled: true`，**没用**，
   系统提示第一行还是时间。
2. 才找到真凶：`dsh-onebot-qq/lib/bridge.js` 里注册系统提示的那段

```js
agentCtx.systemPrompt.section({
    name: 'channel:dsh-onebot',
    order: 0,            // 排在最前
    complete: true,      // 独占整个系统提示
    text: () => {
        const header = '（当前时间：' + now + '；工作目录：…）\n\n';
        return header + parts.complete;      // ← 时间塞在最前
    },
});
```

时间精确到秒，放在第 0 位 → 后面 12KB 系统提示 + 11KB 工具定义全部作废。

### 修法

```js
return parts.complete + '\n\n' + header;   // 挪到末尾
```

一行。同时撤掉另外两处无效改动（关错的插件、我在 prompt.js 里重复注入的时间）。

### 结果

| | 前 | 后 |
|---|---|---|
| cached | 0 | **7168** |
| 命中率 | 0% | **24%** |
| 系统提示开头 | `（当前时间：…）` | `## 人设：鲸鲸` |

### 但只到 24%，还有天花板

连续三轮的 `cached` 都是 **7168，一个整数且不随历史增长** —— 说明上游只缓存
了固定的一段（约等于系统提示 12443 字符 ≈ 7K token），**工具定义和对话历史没有
被缓存**。

而请求体里最大的一块恰恰是历史：

```
BODY msgs=202 chars=46208 tools=11184
  user:23848  system:12443  tools:11184  tool:8553  assistant:1364
```

所以再往下压成本要动历史长度，而不是继续折腾前缀。相关旋钮：
`compaction-basic` 的 `headroomTokens: 16384` —— 只在接近模型上限时才压缩，
29K 远没触发，历史会一直涨到十几万才收拾。

# 附三：预算硬上限（budget.py）

## 为什么记账不够

`usage_log` 是**事后**：钱已经花掉了，你只是知道了数字。
真出事（脚本跑飞、循环调用、有人刷）的时候，你需要的是**事前闸门**。

## 两档熔断

```
软线（默认 80%）→ 停「非必要」调用：看图判断、记忆蒸馏
硬线（100%）  → 主对话也停，返回 429 + 明确原因
```

为什么分级：主对话停了她就哑了；但"给图打标签""整理记忆"这类批处理停下
完全无害，第二天额度恢复再跑。所以先砍后者。

拒绝时会返回一句人话，她能如实转告：

```
今日 token 预算已用尽（206,877 / 1,000，20687%）。
这不是故障，是预算熔断。明天零点自动恢复；
要立刻恢复就调高 /opt/dsh/budget.json 的 daily_tokens。
```

## 接在哪

| 入口 | 服务名 | 软线 | 硬线 |
|---|---|---|---|
| `llm_shim.py`（主对话） | agent | 放行 | 429 |
| `seer.py`（看图） | vision | 停 | 停 |
| `memory_distill.py`（蒸馏） | distill | 停 | 停 |

计数来源就是 `usage.jsonl`（同一份数据），按日期分桶，跨天自动归零。
闸门自身出异常时**一律放行**——闸门坏了不能把人锁在外面。

配置 `budget.json`：

```json
{ "enabled": true, "daily_tokens": 3000000, "soft_ratio": 0.8 }
```

## 实测

```
硬线设 1000 → 今日已用 206,877 → 状态 hard
  主对话      HTTP 429 + 明确文案
  看图调用    (None, "预算已用尽…")
  蒸馏        RuntimeError("预算已用尽…")

软线设 300,000（已用 68%）→ 状态 soft
  主对话      放行（401 是上游没 key，说明过了闸门）
  看图        停
```

# 附四：入库图片的内容风险筛查

## 之前是「有代码、没跑过」

`judge_safe()` 早在 `ingest` 里，但只有她主动调 `ingest` 才触发。
实测全库 4130 条：**只有 1 条有 `safe` 字段，判定"不适合转发"的 0 条**。

而结算（`media_triage`）问的是"值不值得收"，把隐私混在"不值得收"的理由里，
不产出 `pick()` 能用的标记。等于**内容风险筛查从未真正生效**。

## 现在合并进同一次调用

结算那一次模型调用同时产出四个字段：

```
值得收? | 场景 | 适合转发? | 理由
```

prompt 里把 safe 单独定义（隐私、真人自拍、擦边、政治敏感、暴力血腥、
侮辱特定人群），并写明理由：**表情包会被随手转到别的群，泄一次收不回来**。

落盘规则：

```
值得收 + 安全    → 复制进 pending/（照常）
值得收 + 不安全  → 挡在 pending 之外，并写 extras[sid].safe=False
不值得收         → 删除（照旧）
```

`pick()` 本来就会跳过 `safe is False` 的条目，所以这一步补上之后，
**风险图即使混进来了也发不出去**。

`safe` 缺失时判为 `None`（不确定），**绝不默认 True**——宁可多留一张让人看一眼。

## 实测

造了一张模拟隐私截图（姓名 / 手机号 / 快递单号 / 地址 / 工牌）：

```
判断：值得收=False 场景=- 安全=False 理由=含姓名电话住址隐私
```

新增 6 个测试钉住：safe=false 解析、缺字段不默认安全、不安全不进 pending、
安全的照常进 pending。

# 附五：看图端点为什么容易配错（v0.3.1 修）

三个坑叠在一起，症状只有一个：**能聊天，但说看不到图片**，而且日志里不报错。

**坑一：`deploy.env.example` 没有 `VISION_BASE` 项**
`install.sh` 让它回落到 `$LLM_BASE_URL`，而示例里那是 `api.deepseek.com`
——纯文本接口，不收图片。

**坑二：占位符打在了错的路径上**
`install.sh` 替换的是 `profiles/web/local-memory/cordis.patch.yml`，
但 npm 把 `local-memory` 复制进 `node_modules`，**运行时读的是
`node_modules/local-memory/cordis.patch.yml`**。于是 `__VISION_BASE__`
原样进了 MCP 配置，请求被发到 `__VISION_BASE__/chat/completions`。

**坑三：MCP 子进程不继承父环境**
dsh 用配置里的 `env:` 段决定子进程环境。所以把 `VISION_BASE` 写进
`qwen.env`（systemd EnvironmentFile）**对 MCP 子进程无效**，必须写进
MCP 配置的 `env:` 段——这也是 `install.sh` 要 sed 那个文件的原因。

同理，`seer.api_key()` 不能只信 `os.environ`：MCP 子进程里没有
`VISION_API_KEY`，得回落到读 `qwen.env`。

## 现在有四道检查

```
install.sh   装之前：指向 api.deepseek.com 就警告"看不见图片"
install.sh   装之后：node_modules 里还有 __VISION_BASE__ 就 die
verify.sh    6.6 真发一张 1x1 的图，HTTP 非 200 判 FAIL
checkall.py  体检（目前不覆盖看图，靠上面三条）
```

关键的教训：**"配置写了"不等于"配置到了"**。第一版我只加了 `qwen.env` 就以为
修好了，实际 MCP 子进程根本读不到——这种失败不会报错，只会表现为"她看不见图"，
和"模型不想看图"几乎无法区分。
